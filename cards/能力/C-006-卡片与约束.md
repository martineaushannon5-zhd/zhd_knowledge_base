# 能力卡：卡片与约束

## 一句话

让 Agent 在开工前把任务变成有边界的任务卡与 Context Pack，而不是直接动手。

## 触发条件

- 收到一个明确的开发/修复/文档任务。
- 需要把需求交接给任意编码 Agent。

## 输入

| 输入 | 必填 | 说明 |
|---|---|---|
| 任务目标 | 是 | 一句话 |
| 范围与允许文件 | 是 | in/out scope、allowed_files |
| 相关事实 | 是 | 检查 last_verified_at |

## 输出

| 输出 | 形式 | 验收 |
|---|---|---|
| 任务卡 | `cards/任务/T-XXX.md` | 字段齐全，Owner 批准 |
| Context Pack | `工作流/context-packs/` | 结构见 docs/agent.md 第 4 节 |

## 约束

- 允许：检索相关能力/事实、按需起草卡片和交接摘要。
- 边界：本卡描述整理能力，不授予业务代码、秘密或规则变更权限；执行权限以用户任务和统一规则为准。
- 依赖：`templates/`、`AGENT-规则.md`。
- 小修改使用明确用户请求；多步交接才需要正式卡片，不强制每个任务生成Context Pack。

## 什么时候不要用

- 纯检索问答，不需要开工。
- 没有明确任务目标，Owner 还没给方向。

## 示例

### 好例子

修 yoji 登录 500：先写任务卡，限定 login.ts 与对应测试，批准后交接。

### 坏例子

“把整个后台优化一下”：范围不清，直接开工会蔓延。
